# 会话回顾

用本技能回顾当前会话，并把结构化反馈条目追加到项目的工作流反馈日志。

## 回顾铁律

三条不可违反的规则，违反任意一条都会让反馈日志失去价值：

1. **不编造对话事实。** 每条反馈必须指向会话中真实发生的轮次——AI 确实答错、闸门确实被跳过、工具确实报错。想不起来的不写，宁可少写。
2. **只记录系统性信号。** 一条反馈的价值在于指向可修的 skill/文档/规则缺口。纯执行失误（用户忘给参数、打字错误）没有修复目标，不写。
3. **不记录秘密。** notes 里不出现令牌、密钥、密码、内网地址、完整报文。日志是给未来的改进决策读的，不是泄露源。

## 反馈存到哪里

默认位置：当前项目根目录下的 `metrics/workflow-feedback.jsonl`。如果项目设定了其他日志位置（查看项目文档或已有日志文件），用那个。首次写入时创建文件；它是只追加的本地状态，绝不提交到 git——首次写入时若 `metrics/` 未被 git 忽略，提醒工程师把它加入 .gitignore。

## 何时使用

- 工程师说"回顾一下这个会话"、"记录会话反馈"或"session review"
- 任何工作流任务的工作会话结束时
- 解决了一个需要多轮来回的问题之后

## 何时不用

- 会话刚开始、还没有可回顾的实质内容 → 说明情况，不生成空条目
- 整场会话只有琐碎澄清、无工作流问题 → 写一条 `success` 即可，不做过度分析
- 工程师只想要对话摘要而非工作流反馈 → 那是总结任务，不是本技能

## 分析什么

回顾对话并识别：

1. **需纠正的错误答案** — AI 给出了错误输出，工程师不得不纠正
2. **跳过闸门** — 跳过了必需的工作流阶段或确认
3. **错误路由** — AI 使用了错误的技能、工作流或方法
4. **MCP 错误** — 工具调用失败或阻塞了工作流
5. **技能/文档缺口** — 因为规则缺失或不清晰而需要反复澄清
6. **多轮纠正** — 需要 2+ 轮交流才能得到正确答案（同一问题的多轮纠正**合并为一条**，并注明轮次数）
7. **成功完成** — 值得作为正面信号记录

每个独立问题写一条反馈条目。如果没有出错，写一条 `success` 条目。

## 如何写反馈

向反馈日志每行追加一个 JSON 对象：

```json
{"timestamp": "2026-11-13T14:30:00+08:00", "platform": "claude", "area": "review", "result": "corrected", "issue_type": "wrong-routing", "priority": "medium", "notes": "<出了什么问题，正确行为应该是什么>", "ref": "PR-123"}
```

| 字段 | 取值 |
|---|---|
| `timestamp` | ISO-8601 本地时间 |
| `platform` | `claude`, `codex`, `codebuddy`, `cursor`, `github-copilot`, `intellij-copilot`, `gemini`, `opencode`, `other` |
| `area` | `planning`, `implementation`, `review`, `git-pr`, `mcp`, `environment`, `docs`, `other` |
| `result` | `success`, `blocked`, `corrected`, `failed` |
| `issue_type` | `none`, `gate-skipped`, `wrong-routing`, `mcp-error`, `skill-sync-missing`, `generated-code-hygiene`, `logging-convention`, `utility-reuse`, `title-format`, `ticket-field`, `auth`, `tool-error`, `other` |
| `priority` | 可选：`low`, `medium`, `high` — 影响范围 × 复发频率 |
| `notes` | 出了什么问题，正确行为应该是什么 |
| `ref` | 可选的工单 / PR 编号 |

从当前 AI 工具推断 `platform`，除非工程师另行指定。

**复发标注：** 追加前扫一眼已有日志——同一 `area` + `issue_type` 若已出现过，这是复发：notes 末尾加 `recurring(第N次)`，且 `priority` 至少 `medium`。复发是规则缺口的 strongest signal。

## 快速参考

| 情形 | 动作 |
|------|------|
| AI 答错、工程师纠正 | 每个独立问题一条 `result=corrected` |
| 跳过必需阶段/确认 | 一条 `gate-skipped` |
| 用错技能、工作流或方法 | 一条 `wrong-routing` |
| MCP/工具调用失败 | 一条 `mcp-error` 或 `tool-error` |
| 因规则缺失反复澄清 | 一条对应缺口的 `issue_type` |
| 2+ 轮才答对 | 合并为一条，注明轮次数 |
| 任务顺利完成 | 一条 `success` |
| 用户忘给参数、打错字 | **不记**（无修复目标） |
| 用户单纯夸奖 | **不记**（除非揭示了某条规则缺失） |

## 规则

- `notes` 控制在 200 字符以内，聚焦工作流中应该改变什么
- **不要**记录琐碎澄清（例如用户只是忘了提供的缺失参数）
- 聚焦系统性问题：表明 skill、文档或工作流规则需要更新的事情
- **不要**提交反馈日志——它是只追加的本地状态

## 异常场景速查

| 码 | 场景 | 处理 |
|------|------|------|
| SR-E01 | 日志文件/目录不可写 | 报告失败原因，把条目内容打印到对话让工程师手动保存；绝不改写其他位置 |
| SR-E02 | 无对话可回顾（刚开会话就被调用） | 说明"没有可回顾的会话历史"，不生成空条目或编造 |
| SR-E03 | 会话中途被调用 | 只回顾到当前为止，声明"回顾截至于当前轮次"，提示会话结束后可再回顾一次；条目正常记录 |
| SR-E04 | JSONL 文件存在但部分行损坏 | 不重写、不删除损坏行；跳过并在汇总表报告"发现损坏行 N 条"，追加从新行开始 |
| SR-E05 | 工程师不认可已记录的某条目 | 不删除（append-only）；新增一条更正条目，notes 指向被更正条目的时间戳 |

## 回顾反模式

发现自己在做以下事情时，**立即停下**：

| 你在做/想的事 | 实际含义 | 正确做法 |
|---|---|---|
| 记录"用户没给参数"这类琐碎澄清 | 没有修复目标 | 按快速参考表跳过 |
| 把用户夸奖记成 feedback | 不是工作流问题 | 仅当它揭示规则缺失才记录 |
| notes 写成小作文 | 超过 200 字符无法消费 | 一句话问题 + 一句话正确行为 |
| notes 里带令牌/密钥/完整报文 | 泄露风险（铁律 3） | 脱敏后记录 |
| 同一问题每轮各记一条 | 刷屏掩盖复发信号 | 合并为一条并标注 recurring |
| 编一条"看起来该有"的反馈 | 日志失去可信度（铁律 1） | 宁缺毋滥，删掉它 |

## 回顾完成检查清单

输出汇总前，逐项确认：

- [ ] 每条反馈对应真实发生的对话轮次（可追溯，无编造）
- [ ] 无琐碎澄清、无夸奖式条目
- [ ] notes ≤ 200 字符且不含秘密/完整报文
- [ ] 同一问题的多轮纠正已合并（recurring 标注复发）
- [ ] 每行 JSON 通过字段枚举校验（platform/area/result/issue_type/priority）
- [ ] 反馈日志未被提交到 git（metrics/ 已忽略或已提醒）
- [ ] 无事发生时写了一条 success

## 写完反馈之后

打印一张简要汇总表：

| 区域 | 问题类型 | 优先级 | 备注 |
|------|---------|--------|------|
| ...  | ...     | ...    | ...  |

然后根据发现的问题，建议当前项目中哪些文件可能需要更新——这是反馈闭环的下半段：**日志记下信号，文件建议把它变成行动**。

## 常见问题

**Q: 为什么不把反馈日志提交到 git？**
A: 它是本地工作状态，包含开发过程的试错细节，提交会把个人工作流噪音带进团队仓库。工程师可自行决定是否归档。

**Q: 记错了怎么办？**
A: 日志是 append-only，不删除——新增一条更正条目，notes 指向被更正条目的时间戳（见 SR-E05）。错误的记录 + 更正本身也是一条工作流信号。

**Q: 日志越积越大怎么办？**
A: 本技能只负责追加。体量影响读取时由工程师决定归档或清理策略；recurring 标注会帮助识别哪些模式已被吸收进规则、可以归档。

**Q: 和 self-improving 类技能是什么关系？**
A: 定位互补：它们面向持续学习、把通用经验晋升到 AGENTS.md 等工作区文件；本技能专注会话级工作流问题的结构化提取。本技能的日志输出可以直接被它们当作输入消费。

## 语言支持

本技能支持中英文交互。触发词包括"回顾一下这个会话"、"记录会话反馈"、"会话复盘"、"session review"、"log session feedback"、"retrospective"。notes 用会话的主要语言记录。
